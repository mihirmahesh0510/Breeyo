<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| staff client → authenticated WhatsApp API | JWT-bearing requests carrying query, param and body input |
| JWT claims → tenant scope | activeClinicId decides which clinic's data is reachable |
| free-text search → database query | Staff-supplied strings reach query construction |
| route plugin → BullMQ workers | Worker construction at registration time affects the test environment |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-07-12-01 | Elevation of Privilege | client sending its own clinicId to read another clinic's threads | mitigate | Controller reads clinicId only from `request.user.activeClinicId` (the `emr.controller.ts:45` precedent); acceptance criteria greps for zero `body.clinicId` references and an integration case asserts a body-supplied clinicId is ignored |
| T-07-12-02 | Information Disclosure | thread existence disclosed by a 403 on a cross-tenant id | mitigate | `getThread` throws 404 `THREAD_NOT_FOUND`; acceptance criteria asserts no 403 path exists in the inbox service |
| T-07-12-03 | Tampering | SQL injection through the five-field inbox search | mitigate | Prisma parameterized builders with `contains`/`mode: 'insensitive'` only; acceptance criteria asserts zero `$queryRaw`/`$queryRawUnsafe`/`$executeRawUnsafe` in the inbox service, deliberately not copying `prisma-rls.ts:19-21` |
| T-07-12-04 | Elevation of Privilege | a role without SEND_WHATSAPP sending messages to pet owners | mitigate | `requirePermission('SEND_WHATSAPP')` preHandler on send and retry; integration cases cover FrontDesk and Clinician allowed, a lacking role 403, and no Authorization 401 (D-20). Seeded permissions are asserted unchanged |
