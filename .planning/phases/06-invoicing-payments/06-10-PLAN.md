<objective>
Implement BIL-06: payment confirmation that updates invoice status automatically, plus the two server-side sweeps that make D-11 and D-23 real.

Four Razorpay webhook constraints are non-negotiable and each has a specific failure mode. Signature verification requires the **raw, unparsed** body — Fastify's default JSON parser produces an object whose `JSON.stringify` will not byte-match Razorpay's payload, so verification would fail on 100% of real traffic while appearing to work against a hand-crafted curl payload. Responses must be 2xx within **5 seconds** or Razorpay retries with exponential backoff for 24 hours and then **disables the webhook**, silently breaking BIL-06 for that clinic forever. The same event is delivered more than once by design, so idempotency must be a unique index rather than an application-level check. And events arrive out of order — `payment_link.paid` may precede `payment.captured` — so re-applying `PAID` to an already-`PAID` invoice must be a no-op, not an error.

D-29's per-clinic keys create a routing problem: one deployment, one URL, but a different webhook secret per clinic, and the body cannot be trusted before verification. The chosen design is a per-clinic unguessable path token, which resolves clinic → secret from the path alone with no trial verification and no parsing of unauthenticated input.

The two crons exist because a client countdown is cosmetic: the front desk will background the app, and D-11's "pending payments timeout after 15 minutes and revert to unpaid" must hold regardless.

Purpose: BIL-06 and the automatic half of BIL-03.
Output: webhook route, service, BullMQ worker, two crons, app wiring, and integration tests covering signature, idempotency, latency and the sweeps.
</objective>

`webhook.routes.ts` — a default-export async plugin. First statement:

`fastify.addContentTypeParser('application/json', { parseAs: 'buffer' }, (_req, body, done) => done(null, body));`

This is scoped to this plugin instance only. It must **never** be registered globally — that would break every other JSON endpoint. Register the plugin in `app.ts` as its own registration so the scoping holds.

Route: `fastify.post<{ Params: { webhookToken: string } }>('/webhooks/razorpay/:webhookToken', { config: { rateLimit: false } }, handler)`. No `authenticate`, no `tenantContext` — Razorpay has no JWT. `config: { rateLimit: false }` is required because a Razorpay retry storm exceeding the global 200/min would return 429, Razorpay counts non-2xx as failure, and after 24 hours of failures it disables the webhook for that clinic. The compensating controls are the unguessable path token and the HMAC signature, both stronger than IP rate limiting.

Handler sequence, in this exact order:
1. Read `request.body as Buffer`, `x-razorpay-signature` and `x-razorpay-event-id`. Return 400 immediately if either header is missing — before any database access, so a malformed flood costs nothing.
2. `resolveClinicByWebhookToken(token)` against `getBasePrisma()` (there is no tenant context; the token *is* the tenant assertion). Return 404 on no match.
3. `decryptSecret(clinic.razorpayWebhookSecretEnc)`; if the column is null, return 404 rather than 500 — a clinic that has not configured a webhook secret is indistinguishable from an unknown token from the caller's perspective, which is the correct information posture.
4. Compute `crypto.createHmac('sha256', secret).update(raw).digest()` and compare against `Buffer.from(signature, 'hex')` using a length check followed by `crypto.timingSafeEqual`. Do **not** use the SDK's `Razorpay.validateWebhookSignature` — 06-RESEARCH.md verified it uses a plain `===` string comparison in `dist/utils/razorpay-utils.js`. On mismatch: `request.log.warn({ clinicId: clinic.id }, 'razorpay webhook signature mismatch')`, write the `WEBHOOK_SIGNATURE_REJECTED` audit row via `writeBillingAuditLogSafe`, return `reply.status(400).send()` with no reason.
5. Insert the `webhook_events` row with `ON CONFLICT (event_id) DO NOTHING` semantics. Implement with `prisma.webhookEvent.create` inside a try/catch on Prisma error `P2002`, or with `$executeRaw` using an explicit `ON CONFLICT DO NOTHING ... RETURNING id`. On a duplicate (zero rows inserted), return 200 immediately without enqueuing — this is the documented duplicate-delivery case and double-enqueuing means double-marking an invoice paid.
6. `await enqueueWebhookJob({ webhookEventId })` on a BullMQ queue named `billing-webhook`, with the payload carrying **only** the row id, never the raw Razorpay body — the durable record is the database row.
7. `return reply.status(200).send({ received: true })`. Target under 500ms; the hard budget is 5 seconds.
