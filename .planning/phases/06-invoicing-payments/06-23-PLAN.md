<objective>
Build the billing settings screen — the phase's most sensitive client responsibility.

Split from plan 06-18 for context budget: that plan owns Quick Sale and the pet-profile Invoices tab; this plan owns settings alone, because settings is where a live Razorpay secret gets typed into a phone and where an unregistered clinic can be nudged into committing a tax offence. Neither deserves to share a context window with a POS cart.

The server returns only `hasRazorpayKeySecret` and `hasRazorpayWebhookSecret` booleans — never the secret, encrypted or otherwise — so the form must be built around write-only credential fields: an empty input means "leave unchanged", not "clear". Sending an empty string on an unrelated settings save would silently break every future payment for that clinic.

It must also enforce the GST-off default, because most solo vets are below the ₹20 lakh registration threshold and an unregistered clinic that prints a GST line commits a Section 122 offence. The UI-SPEC's placeholder of `18` on the GST rate field nudges every clinic toward charging tax, so the rate field stays disabled until a GSTIN passes the format regex and the placeholder is not used.

The screen also surfaces the webhook URL and a configured indicator. D-29's per-clinic keys mean each of the 20 pilot clinics must paste a distinct URL into their own Razorpay dashboard; without a visible indicator, a clinic that skipped that step has BIL-06 silently broken with no symptom until an owner's payment never lands.

Purpose: BIL-05's configuration, BIL-06's webhook enablement, and BIL-07's per-clinic GST switch.
Output: one route, one screen, one component, one hook module, and one test file.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| settings form → credential storage | A live Razorpay secret is typed into a phone and transmitted to the API |
| settings response → form state | Anything the server returns can end up in client memory and on screen |
| GST toggle → printed invoice | Enabling GST without registration turns every subsequent invoice into a compliance exposure |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-06-117 | Information Disclosure | a Razorpay secret rendered or held in form state | mitigate | The server returns presence booleans only; the inputs are always initialised empty with `secureTextEntry`; a test asserts no rendered text or form state matches the ciphertext or key-id shapes |
| T-06-118 | Tampering | an empty secret field clearing a working credential on an unrelated settings save | mitigate | Credential keys are omitted from the payload entirely when the input is empty; a test inspects the request body and asserts the key's absence; the server treats absence as unchanged |
| T-06-119 | Elevation of Privilege | a non-Admin reaching the settings form and being told only at save time | mitigate | The screen is gated on `MANAGE_CLINIC_SETTINGS` from the auth context and renders an access-denied state, in addition to the server's 403 |
| T-06-120 | *(compliance, not STRIDE)* | a clinic below the ₹20 lakh threshold enabling GST — Section 122 offence | mitigate | GST defaults off; the rate field is disabled until a `GSTIN_REGEX`-valid GSTIN exists; the shared schema rejects `gstEnabled` without a GSTIN; an explanatory caption states the threshold rule; the `18` placeholder is explicitly not used |
| T-06-121 | Denial of Service | BIL-06 silently broken for a clinic that never configured its Razorpay webhook | mitigate | The webhook URL is displayed with a copy action and a configured/not-configured indicator driven by the server's `webhookConfigured` flag |
| T-06-140 | Information Disclosure | a rotated webhook token leaving the previous one live because the form kept stale state | mitigate | `useRotateWebhookToken` invalidates the settings query on success so the displayed URL is always the current one; the summary records the observed rotate-then-refetch behaviour |
</threat_model>
