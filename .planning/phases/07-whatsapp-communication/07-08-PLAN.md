<objective>
Build the outbound send path: the template registry, the repository, the BullMQ queue wrappers, the send-authorization gate (permission, consent, STOP, category), and the persist-then-dispatch send service.

Purpose: this is where WHA-02 (invoice delivery) and the server-side half of WHA-05 (every flow logged) actually happen, and where D-10 through D-13 and D-18 become enforced behavior rather than intentions. The persist-then-dispatch shape matters beyond tidiness: UI-SPEC's success toast is literally `Message queued` and the thread must show a Queued bubble immediately, Retry needs a row to target, and a QUEUED row must survive Redis loss. Calling the provider inside the HTTP request would make the Queued → Sent → Delivered ladder unimplementable.

Output: registry, repository, queues, authorization service, send service, three unit suites and three real-database integration suites (send, opt-out, consent).
</objective>
