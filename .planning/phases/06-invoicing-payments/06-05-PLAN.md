<objective>
Build the GST engine and the money boundary adapter as pure, I/O-free, exhaustively unit-tested functions.

This is the one place in Phase 6 where hand-rolling is correct: there is no npm package that models Indian GST for this use case, and every candidate is either a rate table gone stale after GST 2.0's 22 Sept 2025 slab change, a GSTN e-invoicing wrapper irrelevant below the ₹5 crore threshold, or a generic sales-tax library with no concept of exempt supplies, place of supply or CGST/SGST splitting.

Correctness here is legally load-bearing. Veterinary healthcare services are exempt under Notification 12/2017-CT(R) Entry 46 (SAC 998351) while pet food, accessories and dispensed medicines are taxable, so a flat rate applied uniformly would invent tax liability that does not exist. Rounding is per tax head at invoice level per Section 170 and Rule 51 — per-line rounding accumulates error and will not reconcile with GSTR-1. And an invoice-level discount must reduce the taxable value before tax is computed (Section 15(3)(a)), not be subtracted from the grand total afterwards.

Purpose: BIL-07. Structuring this as pure functions with no `PrismaClient` in scope makes it trivially RED-first testable and auditable, which matters more here than anywhere else in the codebase.
Output: `money.ts`, `gst.service.ts`, and two unit test files with no database dependency.
</objective>

Create `apps/api/src/modules/billing/gst.service.ts` as a pure module — no `PrismaClient` in any signature, no `async`, no `await`. Use 06-RESEARCH.md's `## Code Examples -> GST calculation` as the source implementation; it is already written against these conventions.

Export two functions.

`allocateInvoiceDiscount(lines, invoiceDiscountPaise)` — pro-rates the invoice-level discount across **all** lines by `lineTaxable` weight using `allocateProRata` from `money.ts`, returning each line's `allocatedInvoiceDiscountPaise` and its post-discount `taxableValuePaise`. Exempt lines participate in the allocation (D-07 promised the owner a discount on the whole invoice) but contribute nothing to the tax base. Under GST Section 15(3)(a) a discount known at the time of supply reduces the taxable value, so this must run **before** tax computation, never as a subtraction from the grand total (Pitfall 5).

`computeInvoiceTax(lines: TaxableLine[], opts: { gstEnabled: boolean; isInterState: boolean }): TaxBreakdown & { lines: PerLineTax[] }` — where `TaxableLine` is `{ lineId, taxableValuePaise, gstRatePercent, taxTreatment, hsnSacCode }`.

Order of operations, exactly:
1. If `!opts.gstEnabled`, return all heads zero, `roundOffPaise: 0`, `documentType: 'invoice'`, and per-line zeros. Early-return before any rate validation so an unregistered clinic with stale rate data still produces a clean invoice.
2. Validate every `gstRatePercent` against `GST_RATE_SLABS`; throw on a miss.
3. Per line: if `taxTreatment !== 'taxable'` or `gstRatePercent === 0`, all three heads are zero. Otherwise `total = Math.round(taxableValuePaise * gstRatePercent / 100)` in exact paise with no intermediate rounding; if inter-state, `igst = total`; else `half = Math.floor(total / 2)`, `cgst = total - half`, `sgst = half` so the two heads sum exactly to `total` and the odd paise lands on CGST by convention.
4. Sum each head across lines to get the exact totals.
5. Round each head **once, at invoice level**, to the nearest whole rupee: `Math.round(exact / 100) * 100`. `Math.round` is half-up for positive values, matching Section 170's "≥ 50 paise rounds up".
6. `roundOffPaise` = the sum of the three `(rounded - exact)` deltas.
7. `documentType`: `hasTaxable && hasExempt` → `invoice_cum_bill_of_supply` (CGST Rule 46A); `hasTaxable` only → `tax_invoice`; otherwise → `bill_of_supply`. Where `hasExempt` means any line whose `taxTreatment !== 'taxable'`.
8. `grandTotalPaise` = `taxableValuePaise + cgstPaise + sgstPaise + igstPaise + roundOffPaise`.
