<objective>
Wave 0c (D-30, the part 06-PATTERNS.md Warning 4 identified as the real root cause): make the tenant client actually be used.

`request.db` is set by `tenantContext` on every authenticated request and is consumed by exactly zero modules. `emr.routes.ts:12`, `queue.routes.ts:9`, `patient.routes.ts:9`, `drug.routes.ts:9`, `vaccination.routes.ts:9`, `attachment.routes.ts:8`, `notification.routes.ts:10` and `clinic.routes.ts:10` all construct their repositories with `fastify.prisma` — the `breeyo_admin` client, which bypasses row-level security by design — and `emr.controller.ts:263` reaches for `request.server.prisma` directly. Plan 06-00 fixed the tenant client; without this plan that fix changes nothing at runtime, and Phase 6's invoice, payment and Razorpay-credential tables would be added on top of a boundary that is demonstrably bypassed.

Purpose: an IDOR on billing data exposes another clinic's revenue. RLS is the second layer of the defence-in-depth the security research calls for; this plan makes the first layer real for the routes that already exist, and establishes the pattern that plan 06-08's billing routes will follow.
Output: per-request service construction from `request.db` across six clinic-scoped modules, plus HTTP-layer cross-tenant tests.

Scope note: this plan was split for context budget. The remaining two modules (notifications, clinic), the three documented admin-client exemptions and the `scripts/check-tenant-client.sh` CI gate are plan 06-20, which depends on this one. The gate is deliberately written after the bulk conversion lands so it needs no temporary allowlist. Later plans in this phase reference `bash scripts/check-tenant-client.sh` in their acceptance criteria; that script exists from wave 3 onward, which is before any of them run.
</objective>
