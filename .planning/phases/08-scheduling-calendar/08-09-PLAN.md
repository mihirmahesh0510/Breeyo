<objective>
Deliver the mechanism that actually makes SCH-02 true: a single short-interval BullMQ sweep that turns due appointments into `EXPECTED` queue entries, flips abandoned expected entries to `NO_SHOW` after the grace window, and fires the staff pushes D-27 asks for.

Purpose: RESEARCH Pattern 2 is explicit that one `upsertJobScheduler` job running every 5 minutes IST over Postgres-owned state is the right answer, and that per-appointment BullMQ delayed jobs are not — this project's Redis runs `allkeys-lru` eviction and the booking horizon is 90 days, so a long-delay job can be silently evicted. `node-cron` is equally wrong because `infra/aws/` deploys multiple ECS tasks and an in-process cron fires once per process. `08-PATTERNS.md` § No Analog Found records `upsertJobScheduler` as the one genuinely new BullMQ API in this repo, and RESEARCH Pitfall 4 records the exact test-flakiness trap to avoid when constructing the worker.
Output: a handoff service, a push-trigger service, the sweep worker, a backlog hook in the existing queue service, and integration tests proving idempotency.
</objective>

`async autoFlipExpiredExpected(now: Date, graceMinutes = NO_SHOW_GRACE_MINUTES, limit = 200): Promise<{ entriesFlipped: number; appointmentsFlipped: number }>`:
1. Compute `cutoff = new Date(now.getTime() - graceMinutes * 60000)` and call `this.appointments.findExpiredExpected(cutoff, limit)`.
2. For each appointment, load its pets' queue entries. Flip only the entries still in `EXPECTED` to `NO_SHOW` with `completedAt: now`.
3. Mark the appointment `NO_SHOW` via `appointmentService.markNoShow` ONLY when no pet on that appointment attended (every entry was still `EXPECTED`). 4. Broadcast `QUEUE_UPDATED` and `APPOINTMENT_UPDATED` once per appointment.

Both methods must be safe to call concurrently with themselves: rely on the marker columns in the driving query plus the `@@unique([appointmentId, petId])` constraint, exactly as RESEARCH Pattern 2 prescribes ("the unique task key makes a duplicate sweep a no-op anyway. ## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| background worker → queue and appointment tables | Privileged writes happen with no authenticated user present and no clinic scope |
| Redis → sweep scheduling | Job scheduling state lives in a cache configured with `allkeys-lru` eviction |
| sweep → staff devices | The sweep can cause a push notification to every staff phone in a clinic |
