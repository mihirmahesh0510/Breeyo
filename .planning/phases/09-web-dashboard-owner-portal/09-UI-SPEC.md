# Phase 9 — UI Design Contract

> Visual and interaction contract for the Breeyo web dashboard and owner portal. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

---

## Design System

| Property | Value |
|----------|-------|
| Tool | none — shadcn explicitly declined for Phase 9; use the shared Breeyo token system and manual web components instead (User input 2026-05-07) |
| Preset | not applicable |
| Component library | Custom Next.js web components built on the Phase 2 Material Design 3 foundation and Breeyo CSS custom properties; do not introduce a second component system for web (02-CONTEXT D-01, 09-CONTEXT D-41) |
| Icon library | Material Icons / Material Symbols base plus custom veterinary SVGs where needed (02-CONTEXT D-08) |
| Font | Inter on web; weights limited to 400 and 500; use shared token export path from `packages/ui/src/theme/portal.css` / generated CSS custom properties for both dashboard and owner portal (02-UI-SPEC token bridge, User input 2026-05-07) |

### Phase 9 Surface Split

- **Web dashboard:** operational browser surface for Admin by default and Front Desk when enabled; hide unauthorized modules entirely (09-CONTEXT D-15 to D-21).
- **Owner portal:** no-login, tokenised, mobile-responsive web surface for owners; records are read-only, payments happen through explicit Razorpay handoff and return (09-CONTEXT D-46 to D-72, REQUIREMENTS OWN-01 to OWN-06).
- **Shared rule:** browser and mobile must preserve the same workflow meanings, statuses, and vocabulary even when browser layouts are denser (09-CONTEXT D-38 to D-41).

## Spacing Scale

Declared values (must be multiples of 4):

| Token | Value | Usage |
|-------|-------|-------|
| xs | 4px | Icon gaps, badge offsets, inline metadata spacing |
| sm | 8px | Compact chip spacing, table-cell breathing room, inline action groups |
| md | 16px | Default card padding, form field spacing, panel interiors |
| lg | 24px | Section padding, dashboard panel interiors, portal content spacing |
| xl | 32px | Gaps between priority panels and page-level section groups |
| 2xl | 48px | Major dashboard section breaks and roomy portal summary separation |
| 3xl | 64px | Page-level top/bottom spacing on desktop and tablet layouts |

Exceptions: minimum interactive hit area is **44x44px** for every button, icon button, tab, and row action (02-CONTEXT D-28); dense operational tables may use **40px visual rows** in inventory/billing grids, but each row action must still keep a 44px click target; owner portal keeps **16px horizontal padding** on mobile and a **480px max readable content width** on larger screens (02-UI-SPEC owner portal notes, REQUIREMENTS OWN-05).

## Typography

| Role | Size | Weight | Line Height |
|------|------|--------|-------------|
| Body | 16px | 400 | 1.5 |
| Label | 14px | 500 | 1.4 |
| Heading | 20px | 500 | 1.2 |
| Display | 28px | 500 | 1.2 |

Type rules:
- Use only **four sizes** in Phase 9: 14, 16, 20, 28.
- Use only **two weights** in Phase 9: 400 and 500.
- Dashboard page titles use **Display 28/500**.
- Dashboard panel titles, tab labels, dialog titles, and portal section titles use **Heading 20/500**.
- Table headers, status labels, secondary actions, helper text labels, and meta rows use **Label 14/500**.
- All descriptive text, record glosses, invoice copy, and help copy use **Body 16/400**.
- Owner-facing record language must keep the clinic term visible and add a plain-language gloss below in the same 16px body style when needed (09-CONTEXT D-73 to D-77).

## Color

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | `#FFFBF5` | Browser page background, portal background, panel surfaces, drawers, modal bodies |
| Secondary (30%) | `#F5F0EB` | Cards, cockpit panels, sticky headers, side navigation surfaces, trust/info banners, table chrome |
| Accent (10%) | `#2E7D32` primary accent with `#E65100` warning accent reserved for exception states only | Primary CTAs, active navigation, selected filters, checkout/pay actions, approval states; warning accent only for overdue, low-stock, expiring, and urgent exception chips |
| Destructive | `#BA1A1A` | Destructive actions only |

Accent reserved for: primary quick-action buttons on dashboard home; active sidebar/nav state; selected schedule or inventory filter chips; owner portal **Pay Invoice** / **Pay Selected Invoices** actions; success receipt/download actions; overdue invoice badges; low-stock and expiring-batch badges; queue/schedule conflict prompts that require action. Accent is never used for body copy, table text, passive borders, or decorative fills. Destructive red is limited to invoice voids, refunds, access removal/deactivation, invalid-link states, and irreversible stock-change confirmations.

## Copywriting Contract

| Element | Copy |
|---------|------|
| Primary CTA | Dashboard home: **Review Alerts**. Owner portal invoice flow: **Pay Invoice** for single invoice and **Pay Selected Invoices** for multi-invoice checkout. |
| Empty state heading | Dashboard: **Nothing needs attention right now**. Owner portal records: **No records for this pet yet**. Owner portal invoices: **No invoices yet**. |
| Empty state body | Dashboard: **Today's queue, schedule, billing, and stock are up to date. Open a panel below to review details.** Owner portal: **Your clinic will add visit records and invoices after your next appointment. If you need help now, contact the clinic below.** |
| Error state | Dashboard: **Could not refresh live clinic data. Retry this panel or reopen the module.** Owner portal: **We couldn't open this page or complete payment. Try again, request a fresh link, or contact your clinic.** |
| Destructive confirmation | **Void invoice:** “Void invoice {number}? This keeps the audit trail and may return stock.” **Refund payment:** “Refund ₹{amount} for invoice {number}? This cannot be cancelled after submission.” **Remove batch/adjust stock:** “Apply this stock change? Reason and actor will be recorded.” **Change browser access / role:** “Update access for {name}? Hidden modules will disappear immediately.” **Cancel appointment:** “Cancel this appointment? The owner and staff schedule will update immediately.” |

### Copy Rules

- Use short, direct, operational copy in the dashboard.
- Use warm, plain-language reassurance in the owner portal.
- Prefer `[Verb] [Noun]` labels for primary actions.
- Expired-link copy must always include the 7-day rule and a clear WhatsApp reissue path (REQUIREMENTS OWN-04, 09-CONTEXT D-64, D-67).
- Payment failure copy must always present a retry path and clinic contact path (09-CONTEXT D-72, D-79 to D-81).

## Layout & Interaction Contract

### Web Dashboard

| Area | Contract |
|------|----------|
| Home landing | Land on an **operations cockpit**, not analytics-first and not a static module launcher (09-CONTEXT D-01). |
| Scroll order | Home sections render in this order: **Alerts & Exceptions → Queue → Scheduling → Billing → Inventory → User Management → Owner/WhatsApp Exceptions** (09-CONTEXT D-06, D-11, D-12, D-13). |
| Panel model | Use vertically stacked, scrollable priority panels. Do not force a rigid fixed grid. Inner card groups may use responsive columns, but the home page itself remains a prioritized scroll narrative (09-CONTEXT D-05). |
| Information density | Use action-ready snippets, not analytics-heavy charts. Each panel must show just enough context to decide the next click (09-CONTEXT D-08). |
| Quick actions | Every home panel must include at least one direct action: queue move/check-in, appointment open/check-in, invoice collect, batch adjust/open item, user access review, or exception resolution (09-CONTEXT D-03). |
| Search | Search is **module-local only**. No global command bar in Phase 9 (09-CONTEXT D-10). |
| Permissions | Hide modules and actions the user cannot access. Do not render locked placeholders (09-CONTEXT D-20). |
| Clinic switching | Show clinic switcher in the web shell/header using the existing multi-clinic mental model from Phase 1; switching must visibly change the scoped clinic label before content updates (01-CONTEXT D-22 to D-24). |
| Realtime | Updates are inline-first. Use toasts only for failures, action-blocking exceptions, and confirmation of high-value actions; do not toast every normal sync event (09-CONTEXT D-42 to D-45). |
| Conflict handling | When browser and mobile edits collide, show a stale-state banner or row-level warning with **Refresh** and **Review changes** actions; never silently overwrite without surfacing that the data changed elsewhere (09-CONTEXT D-40). |
| Sensitive actions | High-risk actions require confirmation dialog/drawer + visible actor attribution + timestamp in the affected row or detail panel (09-CONTEXT D-23, D-24). |

### Dashboard Navigation

- Use a **left sidebar on 1024px+** with: Home, Queue, Scheduling, Billing, Inventory, Users, and Settings when authorized.
- Use a **collapsible drawer navigation from 768px to 1023px** with the same order.
- Keep page-level actions in a sticky top bar: clinic switcher, current user, current role badge, and module-local search/action slot.
- Home is the default browser route; modules open in full-depth views from the shell, not modal-only surfaces.

### Module Depth Rules

| Module | Contract |
|--------|----------|
| Inventory | Richest browser module. Use sub-tabs: **Stock & Batches** (default), **Reordering**, **Analytics**. Default to direct table actions for normal work; require stronger confirmation for high-risk stock changes (09-CONTEXT D-26 to D-36). |
| Queue | Operational but lighter than inventory. Keep queue and schedule as separate panels and separate module pages even when shown together (09-CONTEXT D-07, D-27). |
| Scheduling | Keep the larger-screen planning surface from Phase 8; week planning belongs here, not on mobile. Quick actions open drawer/bottom sheet first, then deeper edit if needed (08-CONTEXT D-03, D-12). |
| Billing | Support collection, unpaid/overdue review, invoice detail, refund/void admin actions, and payment history. Refunds and voids stay Admin-only (09-CONTEXT D-22, 06-CONTEXT D-20 to D-27). |
| User management | Show an inline awareness mini-panel on home plus a full admin module. Phase 9 user management covers browser access, role toggles, status, and audit visibility; do not turn it into a broader HR/staffing platform (09-CONTEXT D-11, D-21, D-28). |

### Owner Portal

| Area | Contract |
|------|----------|
| Landing | Default to **Overview** for valid links unless the owner opened a deep link to a specific invoice or visit (09-CONTEXT D-46, D-60, D-63). |
| Top-level navigation | Use top tabs: **Overview**, **Records**, **Invoices**. Payments stay inside invoice flows; do not add a separate Payments tab (09-CONTEXT D-57, D-62). |
| Pet context | Multi-pet owners use a **pet switcher** under the trust banner. Switching pets updates Records and Invoices within the same shared portal shell (09-CONTEXT D-58, D-59). |
| Overview | Show a combined summary block at the top when there is both an unpaid balance and a recent clinical update; neither billing nor records should dominate alone (09-CONTEXT D-47 to D-49). |
| Trust | Always show a visible trust banner explaining that the portal is a secure clinic link, valid for 7 days, with no login required (09-CONTEXT D-56, D-65, REQUIREMENTS OWN-04). |
| Records | Present read-only visit history as a timeline. Each visit row shows clinic date, diagnosis, and prescription cards, with owner-friendly glosses where useful (09-CONTEXT D-61, D-73 to D-77). |
| Invoices | Invoices remain pet-scoped in navigation. The owner may still select invoices across pets into one combined checkout with clear pet and invoice breakdown before handoff (09-CONTEXT D-59, D-69, D-70). |
| Payment flow | Before opening Razorpay, show a concise handoff sheet: amount, invoices included, pet breakdown, secure external payment note, and return expectation. After return, show success or failure summary before navigating away (09-CONTEXT D-66, D-71, D-72). |
| Expired links | Expired links render a dedicated expired state with a built-in **Request New Link** action. Invalid/tampered links render a 403-style invalid state with no data and clinic contact only (REQUIREMENTS OWN-04, OWN-06; 09-CONTEXT D-64, D-67). |
| Contact actions | Show **Call Clinic** and **WhatsApp Clinic** actions in the sticky footer or persistent help bar on every portal screen (09-CONTEXT D-52, D-79). |
| Continuity | Within the valid token window, restore the owner to the last viewed tab and selected pet after refresh or return from payment (09-CONTEXT D-53). |

## Screen States Contract

### Dashboard State Rules

- Every dashboard panel must implement **loading, empty, populated, and error** states.
- Loading states use skeletons that match final card/table structure.
- Empty states must still show the panel title and the next available action.
- Error states stay panel-local unless the whole page is inaccessible.
- Browser permission-denied routes should redirect to the first authorized module instead of showing a dead-end screen.

### Owner Portal State Rules

| State | Required UI |
|-------|-------------|
| Validating | Centered clinic-linked loading state with trust copy: “Verifying your secure link...” |
| Loading | Trust banner + top tabs + skeleton summary + skeleton visit/invoice cards |
| Populated | Overview or deep-linked tab with active pet context, help actions, and data |
| Empty records | Overview stays intact; Records tab shows empty guidance and clinic help |
| Empty invoices | Invoices tab shows no invoices state without hiding the pet context |
| Expired | Dedicated expired-link page with **Request New Link** and clinic contact |
| Invalid | Dedicated invalid-link page with no portal data, no retry CTA, clinic contact only |
| Payment success return | Success summary with receipt access before any redirect |
| Payment failure return | Failure summary with retry + clinic help |
