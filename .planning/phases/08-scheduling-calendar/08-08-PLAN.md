<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| mobile optimistic cache → rendered queue state | A locally mutated board is shown to staff before the server confirms it |
| staff tap → privileged queue transition | A single tap moves a patient's real-world queue standing |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-08-35 | Tampering | the optimistic rebuild silently dropping the `expected` group, so staff believe nobody is arriving | mitigate | `applyOptimisticStatusChange` (or the inline `onMutate` block) explicitly carries `expected` through, is unit tested for all four groups, and the `onError` rollback restores a deep-equal board; the 300ms `onSettled` invalidation reconciles with the server broadcast |
| T-08-36 | Elevation of Privilege | a client-side tap advancing an expected patient straight to `IN_CONSULT`, bypassing the queue | mitigate | `getNextStatus` deliberately returns `null` for `EXPECTED`, and the server's `QUEUE_TRANSITIONS` (plan 08-01) has no `EXPECTED` to `IN_CONSULT` edge, so even a crafted request is rejected with `400 INVALID_TRANSITION` |
| T-08-37 | Information Disclosure | an expected row exposing appointment detail for a patient outside the active clinic | accept | The board is rendered from the `clinicId`-scoped `GET /api/v1/queue` response (plan 08-04) and the mobile client sends only its own clinic's token; no client-side filtering is relied on |
| T-08-38 | Repudiation | an accidental no-show tap removing a patient with no confirmation | mitigate | Both no-show paths go through `Alert.alert` with the safe option listed first and default, and the destructive label names the action; the server audit-logs the transition |
</threat_model>
