<objective>
Implement payment collection: cash, split, and Razorpay Payment Links, with per-clinic credentials that never reach a device.

Four Razorpay constraints shape this code. `expire_by` must be **at least** 15 minutes in the future, so computing `now + 15*60` and sending it produces intermittent production-only 400s once network latency and clock skew are added — the fix is `now + 16*60` while keeping the user-facing 15:00 countdown and expiring server-side at 15:00 independently. `amount` is in paise with an INR minimum of 100. `reference_id` is capped at 40 characters, so the bare invoice UUID (36) fits and a prefixed form does not comfortably. And a Razorpay API 200 is not money received — only the webhook confirms payment, which is plan 06-10.

D-29 stores credentials per clinic, so the SDK instance is per-clinic and its secret is decrypted from `razorpayKeySecretEnc` at call time and never cached in a way that could be serialised.

Purpose: BIL-05 and the payment half of BIL-03.
Output: the Razorpay client factory, the payment service, payment endpoints, a reusable SDK mock, and unit plus integration tests.
</objective>
