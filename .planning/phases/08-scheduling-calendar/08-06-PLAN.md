**`apps/web/src/lib/api.ts`** — rewrite to match `apps/mobile/src/lib/api.ts` structurally:
- `interface RequestOptions extends RequestInit { token?: string }`.
- `export async function apiClient<T>(path: string, options: RequestOptions = {}): Promise<T>` — destructure `{ token, headers, ...rest }`, send `'Content-Type': 'application/json'` plus `...(token ? { Authorization: \`Bearer ${token}\` } : {})` plus `...headers`, and keep the base URL as `process.env.NEXT_PUBLIC_API_URL || 'http://localhost:3000'`.
- Remove `credentials: 'include'`. The API issues bearer tokens for this path, not cookies; leaving it in would imply a cookie session that does not exist.
- `export class ApiClientError extends Error` with `code: string`, `status: number`, `details?: Record<string, unknown>`, constructed from `data.error?.message`, `data.error?.code` and `response.status` exactly as the mobile client does. Every downstream web component branches on `error.code` (e.g. `SLOT_DOUBLE_BOOKED` in plan 08-14), so the typed error is load-bearing, not cosmetic.

**`apps/web/src/lib/auth-store.ts`** — a tiny non-React module owning token persistence, so nothing else in the app touches `sessionStorage` directly:
- `const STORAGE_KEY = 'breeyo.web.session';`
- `export interface WebSession { accessToken: string; refreshToken?: string; userId: string; userName: string; activeClinicId: string; }`
- `export function readSession(): WebSession | null` — guard on `typeof window === 'undefined'` (Next.js renders this module on the server too) and return `null` there; `JSON.parse` inside a try/catch returning `null` on malformed data.
- `export function writeSession(session: WebSession): void` and `export function clearSession(): void`.
- A file-header comment recording the decision and its tradeoff: the token lives in memory plus `sessionStorage`, deliberately not an httpOnly cookie, so `apps/web` uses the same token-based model as `apps/mobile` rather than introducing a second auth mechanism into the API. `sessionStorage` (not `localStorage`) bounds exposure to the tab's lifetime, and the token is readable by any script running on the origin — accepted for a staff-only internal tool at Beta scope, and recorded as such in this plan's threat model.

**`apps/web/src/lib/AuthProvider.tsx`** — a `'use client'` component exposing a context with `{ accessToken, activeClinicId, user, isLoading, login, logout }`:

- `login(email, password, clinicId?)` — `POST /api/v1/auth/login` via `apiClient`, reading the response as `{ data: ... }`. Read `apps/api/src/modules/auth/auth.controller.ts` `loginHandler` and `auth.service.ts` `login` to determine the exact response field names for the access token, the user and the clinic; do not guess. If the response indicates the user belongs to multiple clinics and no `clinicId` was supplied, call `GET /api/v1/auth/clinics` and surface the list to the caller so the form can render a picker — mirror whatever the mobile login flow already does for this case rather than inventing new behaviour.
- `logout()` — best-effort `POST /api/v1/auth/logout` with the current token, then `clearSession()` and reset state. A failed logout call must still clear local state.
- Export `export function useAuth()` throwing a clear error when used outside the provider, matching the mobile provider's convention.
- Do NOT implement refresh-token rotation, silent refresh or a token-expiry timer. That is Phase 9's session management. Instead, on any `ApiClientError` with `status === 401`, call `logout()` — implement this as an exported helper `handleUnauthorized(error)` the data hooks in plan 08-14 call, and document it in the summary.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| browser → `POST /api/v1/auth/login` | Unauthenticated credential submission from a public origin |
| access token → `sessionStorage` | A bearer credential is persisted in a script-readable store |
| `?next=` query parameter → post-login navigation | Attacker-controllable input determines where an authenticated user is sent |
| browser tab → Socket.IO handshake | The same token authorizes a long-lived realtime connection into a clinic room |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-08-22 | Information Disclosure | XSS on the web origin reading the access token out of `sessionStorage` | accept (with bounding) | Explicitly accepted at Beta scope and recorded in `auth-store.ts`'s header comment. Bounded by: `sessionStorage` not `localStorage` (the token dies with the tab), no `dangerouslySetInnerHTML` anywhere in `apps/web`, no third-party script tags, all rendering through React's escaping, and no refresh token persisted unless the login response requires it. The alternative (httpOnly cookie) would require introducing a second auth mechanism into an API that issues bearer tokens for every other client — a larger change with its own CSRF surface, and Phase 9 owns full session management |
| T-08-23 | Spoofing | open redirect via `?next=` sending a freshly authenticated staff member to an attacker origin | mitigate | `?next=` is accepted only when it is a relative path beginning with `/`; anything else falls back to `/schedule`. Grep-gated, and human-verified by check 9 |
| T-08-24 | Elevation of Privilege | credential stuffing or brute force against `/api/v1/auth/login` from the new web surface | transfer | The API already rate-limits auth endpoints at 20 requests per minute (CLAUDE.md § API) and `auth.service.login` already records failed attempts through `audit-log.ts`; this plan adds a new client, not a new endpoint, so no new control is required. No client-side attempt counter is added, since it would be trivially bypassed and would imply protection the server actually provides |
| T-08-25 | Information Disclosure | login error copy distinguishing a valid email from an invalid one | mitigate | The page renders the server's message verbatim and adds no client-side branching on user existence; the copy contract is "Could not sign in. Check your email and password." for any local failure |
| T-08-26 | Spoofing | a stale or revoked token continuing to be sent on every request | mitigate | Any `ApiClientError` with `status === 401` triggers `logout()` via the exported `handleUnauthorized` helper, clearing the session and bouncing to `/login`; no silent-refresh path exists to mask an invalid token |
| T-08-27 | Information Disclosure | the token being sent to an unintended origin | mitigate | The `Authorization` header is attached only inside `apiClient`, which always targets `NEXT_PUBLIC_API_URL`; no other module in `apps/web` reads the token except the Socket.IO constructor in plan 08-14, which connects to the same base URL |
</threat_model>
