<objective>
Complete the mobile surface: the Quick Sale counter-sale screen, the billing settings form, and the pet-profile Invoices tab.

The settings screen carries the phase's most sensitive client responsibility. The server returns only `hasRazorpayKeySecret` and `hasRazorpayWebhookSecret` booleans — never the secret, encrypted or otherwise — so the form must be built around write-only credential fields: an empty input means "leave unchanged", not "clear". It must also enforce the GST-off default, because most solo vets are below the ₹20 lakh registration threshold and an unregistered clinic that prints a GST line commits a Section 122 offence. The UI-SPEC's placeholder of `18` on the GST rate field nudges every clinic toward charging tax, so the rate field stays disabled until a GSTIN passes the format regex.

The settings screen also surfaces the webhook URL and a configured indicator. D-29's per-clinic keys mean each of the 20 pilot clinics must paste a distinct URL into their own Razorpay dashboard; without a visible indicator, a clinic that skipped that step has BIL-06 silently broken with no symptom until an owner's payment never lands.

Purpose: BIL-01's counter-sale path, BIL-02's Quick Sale surface, BIL-05's configuration, and BIL-07's per-clinic GST switch.
Output: two routes, two screens, four components, two hook modules, one store, an addition to the pet profile, and three test files.
</objective>

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-06-117 | Information Disclosure | a Razorpay secret rendered or held in form state | mitigate | The server returns presence booleans only; the inputs are always initialised empty with `secureTextEntry`; a test asserts no rendered text or form state matches the ciphertext or key-id shapes |
| T-06-118 | Tampering | an empty secret field clearing a working credential on an unrelated settings save | mitigate | Credential keys are omitted from the payload entirely when the input is empty; a test inspects the request body and asserts the key's absence; the server treats absence as unchanged |
| T-06-119 | Elevation of Privilege | a non-Admin reaching the settings form and being told only at save time | mitigate | The screen is gated on `MANAGE_CLINIC_SETTINGS` from the auth context and renders an access-denied state, in addition to the server's 403 |
| T-06-120 | *(compliance, not STRIDE)* | a clinic below the ₹20 lakh threshold enabling GST — Section 122 offence | mitigate | GST defaults off; the rate field is disabled until a `GSTIN_REGEX`-valid GSTIN exists; the shared schema rejects `gstEnabled` without a GSTIN; an explanatory caption states the threshold rule |
| T-06-121 | Denial of Service | BIL-06 silently broken for a clinic that never configured its Razorpay webhook | mitigate | The webhook URL is displayed with a copy action and a configured/not-configured indicator driven by the server's `webhookConfigured` flag |
| T-06-122 | Tampering | a client-computed counter-sale total disagreeing with the invoice, creating a dispute at the counter | mitigate | `QuickSaleTotals` performs no arithmetic and renders a server preview; the cart store holds no total; grep gates assert both |
| T-06-123 | Tampering | a Quick Sale overselling stock | accept | The client cannot prevent this; the server's row-locked transaction is the control. The client renders the resulting per-row shortfall and disables checkout until it is resolved |
| T-06-124 | Information Disclosure | a previous customer's cart persisting into the next sale | mitigate | Store `reset()` on unmount; no Zustand persistence middleware is used |
