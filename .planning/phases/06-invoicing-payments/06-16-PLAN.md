<objective>
Build the invoice builder: the screen where a draft becomes a finalized, numbered, GST-correct invoice.

The controlling constraint is that the client never computes money. The builder shows a live total while the front desk edits, but that total comes from the server's `preview-totals` endpoint, and `finalize` sends only the line items and options — never a total. A client that computed and sent `grandTotal` could be modified to send `1`. The server recomputes from persisted line items on finalize and ignores anything else; the builder's job is to render whatever it returns.

The second constraint is that BIL-02's stock validation is a server 409, not a client check. A read-only pre-check for the banner is a UX affordance; the authoritative validation holds row locks inside the finalize transaction, and the builder must handle the 409 gracefully because the draft may have been assembled minutes earlier.

Purpose: BIL-01's interactive path, BIL-02's client surface, and BIL-07's builder-side presentation.
Output: eight components, two hook modules, one store, and one store test file.

Scope note: this plan was split for context budget. The screen that composes these pieces and the two Expo Router entry points are plan 06-21, which depends on this one. Everything here is independently unit-testable, which is why the seam sits between the pieces and the composition. Do not create `InvoiceBuilderScreen.tsx` in this plan.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| builder state → finalize request | Everything the device sends is untrusted; the invoice's money must not be among it |
| server preview response → displayed total | The number the front desk reads before collecting payment |
| 409 error payload → stock banner | The client renders a claim about inventory it cannot itself verify |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-06-102 | Tampering | a modified client sending `grandTotalPaise: 1` on finalize | mitigate | No total field exists in the store or in any request body these hooks build; a key-enumeration test asserts the store holds no total-shaped key; the input schemas from plan 06-04 do not accept totals; the server recomputes regardless |
| T-06-103 | Tampering | the client computing and displaying a total that diverges from what the server will charge | mitigate | `InvoiceTotalsSection` performs no arithmetic and takes a server-computed `TaxBreakdown`; grep gates forbid `reduce(` and paise addition in the component |
| T-06-104 | Tampering | a discount above 100 percent or a negative quantity reaching the server | mitigate | Shared `invoiceLineItemInputSchema` validation runs client-side before send and server-side on receipt; inline percentage error in `LineItemDiscountInput` |
| T-06-105 | Tampering | a 100x error from a rupee-entered flat discount or custom-service price | mitigate | Rupee-to-paise conversion happens at exactly the two input components, each with a two-decimal-place rejection rule and an explanatory comment; all display goes through `formatPaiseINR` |
| T-06-106 | Repudiation | finalizing against stale stock and overselling | accept | The client cannot prevent this; the server's row-locked finalize transaction is the control. This plan's contribution is the structural shortfall surface: `useFinalizeInvoice` exposes `details.shortfalls` and `StockValidationBanner` renders it. The blocking behaviour is plan 06-21 |
| T-06-107 | Information Disclosure | a previous patient's line items leaking into a new invoice | mitigate | The store exposes `reset()`; the unmount cleanup that calls it is plan 06-21 |
</threat_model>
