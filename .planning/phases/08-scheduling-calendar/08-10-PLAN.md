`async handleOwnerAction(params: { clinicId: string; threadOwnerId: string; action: 'KEEP' | 'MOVE' | 'CANCEL'; appointmentId: string }): Promise<OwnerActionResult>`:
1. Validate the shape with `ownerAppointmentActionSchema`.
2. **Ownership resolution is the security control of this whole plan.** Load the appointment with `this.appointments.findById(params.clinicId, params.appointmentId)` and then require `appointment.ownerId === params.threadOwnerId`. Both `clinicId` and `threadOwnerId` must come from the resolved inbound thread, never from anything in the message payload. On any mismatch or a null appointment, return a single indistinguishable `{ ok: false, reason: 'NOT_ACTIONABLE' }` and log it — do not throw a distinguishing error and do not tell the owner whether the appointment exists. RESEARCH § Security Domain names exactly this threat: a forged `appointment:cancel:<uuid>` for someone else's appointment.
3. Dispatch:
   - `KEEP` — no state change. D-20 has no confirmed state (`SCHEDULED` already implies confirmed), so there is nothing to transition. Send the owner an acknowledgement through Phase 7's send path and return `{ ok: true, applied: 'KEEP' }`.
   - `CANCEL` — call `appointmentService.cancelAppointment` with `scope: 'ONE'`, a `cancelReason` naming the WhatsApp origin, and the owner recorded as the actor in whatever way plan 08-07's params allow (if `cancelledById` requires a `User` id and an owner has none, pass the appointment's `createdById` and put the owner id in the audit `metadata` — record which was done). Then `reminders.cancelPendingForAppointment(id)` and `pushTriggers.notifyOwnerAction(clinicId, appointment, 'CANCEL')`.
   - `MOVE` — do NOT mutate the appointment.
