Authoritative Cloud API facts (07-RESEARCH § WhatsApp Business Cloud API Reference — all cited from Meta docs; do not re-derive):
- Send: POST https://graph.facebook.com/<VERSION>/<PHONE_NUMBER_ID>/messages
- Required envelope on every message: messaging_product 'whatsapp', recipient_type 'individual', to, type
- Send response: { messages: [{ id: 'wamid...', message_status: 'accepted' | 'held_for_quality_assessment' | 'paused' }], contacts: [{ input, wa_id }] } — message_status is NEVER 'delivered'; contacts[].wa_id can differ from contacts[].input (Pitfall 9)
- Body parameters support named parameters: { type: 'text', text: '...', parameter_name: 'pet_name' }
- Interactive reply buttons: max 3 buttons, id max 256, title max 20, body max 1024
- Interactive list: max 10 rows total across all sections, row id max 200, row title max 24, row description max 72
- Media: POST /<PHONE_NUMBER_ID>/media multipart (file, type, messaging_product) returns a media id; 30-day retention; 100 MB; 25 req/s
- Inbound button tap: { type: 'interactive', context: { from, id }, interactive: { type: 'button_reply', button_reply: { id, title } } }; list pick uses interactive.type 'list_reply' with list_reply { id, title, description }
- Template quick-reply buttons arrive DIFFERENTLY — as a `button` object with `payload`/`text` rather than interactive.button_reply. This is 07-RESEARCH Assumption A1 (third-party sources only, not confirmed on an official Meta page). parseInbound MUST normalize both shapes so the assumption being wrong costs nothing.
- Status webhooks: each status object carries id (the wamid), status, recipient_id, timestamp, and on billable events conversation and pricing. Order is NOT guaranteed — read can arrive before delivered.
- Webhook GET handshake: hub.mode, hub.verify_token, hub.challenge — echo the challenge on a token match.
- Webhook POST: X-Hub-Signature-256: sha256=<hex> is HMAC-SHA256 of the RAW body keyed with the app secret; verify before JSON parsing with a timing-safe comparison.
- Error codes to normalize: 131026, 131047, 131049, 132000, 132001, 4, 80007, 130429.

Code to reproduce verbatim: 07-RESEARCH.md § Code Example 3 (verifyMetaSignature and handleVerification).
Analog: apps/api/src/modules/notifications/push.service.ts for the adapter class shape. No analog exists for an external-API mapper or for HMAC verification anywhere in this repo (07-PATTERNS § No Analog Found).
Do NOT add whatsapp-api-js, @whatsapp-cloudapi/client or @whatsapp-cloudapi/types — 07-RESEARCH § Package Legitimacy Audit evaluated and rejected all three. Use built-in fetch and node:crypto.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Meta (public internet) → webhook endpoint | Fully untrusted input; the only unauthenticated surface in the phase |
| API process → graph.facebook.com | Outbound requests carry a long-lived access token |
| raw request body → JSON parser | Signature must be verified over the raw bytes, before parsing |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-07-07-01 | Spoofing | forged webhook injecting fake inbound messages, STOP opt-outs or booking confirmations | mitigate | `verifyMetaSignature` computes HMAC-SHA256 over the RAW body with the app secret and compares using `crypto.timingSafeEqual`; missing, malformed, truncated and non-hex signatures all return false.
