<objective>
Build the invoice detail layer's foundation: the two data hooks every money-moving surface calls, and the six presentation components the detail screen composes.

The design decision that carries the weight is in `InvoiceActionBar`. It gates its buttons off `isValidInvoiceTransition` from `@breeyo/types` — the same table the server enforces — so the UI never offers an action that will 409. A hardcoded per-status list would work on the day it was written and drift from D-20 the first time the state machine changes, and the drift would surface as a front-desk user tapping a button that fails.

The second is that `usePaymentMutations` is the single write surface for money state, so its invalidation list is the only thing standing between a captured payment and a dashboard that still shows the invoice unpaid.

Scope note: this plan was split from the original 06-17 for context budget. The payment collection sheet, the refund and credit-note surfaces, and the detail and credit-note screens that compose all of this are plan 06-22, which depends on this one. Do not create `InvoiceDetailScreen.tsx`, `PaymentCollectionSheet.tsx` or any route file here.

Purpose: BIL-03's manual controls, the data layer for BIL-05 and BIL-06, and the action-bar entry points for BIL-04's print and share.
Output: two hook modules and six presentation components.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| invoice status → offered actions | An action the server forbids must never be offered, or the front desk learns the state machine through 409s |
| mutation success → every cached view of the balance | A captured payment that leaves a stale balance anywhere invites a second collection |
| void confirmation → stock restoration | Whether dispensed items return to inventory is a real inventory decision, not a UI detail |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-06-110 | Tampering | the UI offering an action the invoice's state forbids, producing a 409 or an inconsistent belief | mitigate | `InvoiceActionBar` derives visibility from `isValidInvoiceTransition`; grep gate forbids a hardcoded per-status list; plan 06-22's detail-screen test iterates all seven statuses against the table |
| T-06-113 | Repudiation | showing a stale unpaid status after the webhook confirmed payment, causing a double collection | mitigate | `useInvoice` sets no `refetchInterval` and relies on plan 06-14's socket-driven invalidation; every payment mutation invalidates the detail, list and dashboard keys, so no surface can retain a stale balance |
| T-06-115 | Tampering | voiding without the stock-restoration choice reaching the server | mitigate | `VoidConfirmSheet`'s checkbox value is reported to its callback and sent explicitly as `restoreStock`; plan 06-22 asserts both `true` and `false` paths and their distinct toasts |
| T-06-137 | Information Disclosure | an unregistered clinic's invoice header rendering a GSTIN row, implying a registration it does not hold | mitigate | `InvoiceClinicHeader` omits the GSTIN row entirely when `gstEnabledSnapshot` is false; grep gate asserts the field is read |
| T-06-138 | Repudiation | a payment or refund that happened but is invisible in the history, leaving a dispute with no on-screen record | mitigate | `InvoicePaymentHistory` renders one row per payment **and** per refund with the method icon and transaction reference, and an explicit empty state so "no rows" is a statement rather than a rendering failure |
</threat_model>
