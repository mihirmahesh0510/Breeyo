<objective>
Build the invoice domain: draft assembly from two upstream sources, the single-transaction finalize that assigns the number and validates stock under row locks, the state machine guards, and void with optional stock restoration.

The two hardest correctness requirements land here. BIL-01's quantity cannot come from `Prescription` — that model carries `dispensed` and `inventoryItemId` but no quantity column (verified in `schema.prisma` lines 446-471). It must come from Phase 5's `StockMovement`, which carries `quantity`, `consultationId`, `invoiceId`, `ownerId` and a `unitPrice` snapshot taken at dispense time. And BIL-02's "real time" means the availability check and the deduction hold row locks inside one transaction: a read-only pre-check for the UI banner is desirable but is not BIL-02. Two front-desk devices finalizing invoices for the last box of a drug at the same moment is exactly the case that separates a correct implementation from a demo.

Purpose: BIL-01, BIL-02, BIL-03 and the invoice half of BIL-07.
Output: repository, stock validator and service, with unit tests for the state machine and the service orchestration. HTTP wiring and database integration tests are plan 06-08.
</objective>

Create `apps/api/src/modules/billing/stock-validator.service.ts` as `export class StockValidatorService { constructor(private readonly prisma: PrismaClient) {} }` — the constructor client is used only by `checkAvailability`. `reserveAndDeduct` takes `tx: Prisma.TransactionClient` as its first parameter and must **never** open its own transaction: the whole point of BIL-02 is that the lock, the check and the deduction share the caller's transaction.

`checkAvailability(db, clinicId, lines)` — a grouped aggregate over `StockBatch` filtered to non-expired rows with remaining quantity above zero, compared against the requested quantities. No locks, no writes. Add a comment stating this is a UX affordance and that the authoritative check is `reserveAndDeduct`.

`reserveAndDeduct(tx, clinicId, lines)` — for each product line, in a deterministic order (sort the lines by `inventoryItemId` before iterating so two concurrent transactions acquire locks in the same order and cannot deadlock on a multi-item invoice):
1. `SELECT id, quantity_remaining, expiry_date FROM stock_batches WHERE clinic_id = ${clinicId}::uuid AND inventory_item_id = ${itemId}::uuid AND quantity_remaining > 0 AND (expiry_date IS NULL OR expiry_date > now()) ORDER BY expiry_date ASC NULLS LAST FOR UPDATE` — substituting the actual shipped column names. The `FOR UPDATE` is what makes BIL-02 real; without it this is a TOCTOU race that oversells.
2. Walk the locked rows accumulating until the requested quantity is met. If the accumulated total is short, collect a `StockShortfall` for that item and continue collecting shortfalls for the remaining lines so the 409 reports every problem at once rather than one per round trip.
3. After all lines: if any shortfall was collected, throw the `INSUFFICIENT_STOCK` domain error (`statusCode = 409`, `code = 'INSUFFICIENT_STOCK'`, and a `details` property carrying `{ shortfalls }`) so `error-handler.ts` surfaces it. Note that `error-handler.ts` replaces the message on any status `>= 500`, so this must be 409 or the shortfall detail is lost.
4. Otherwise apply the deductions with `UPDATE stock_batches SET quantity_remaining = quantity_remaining - $n WHERE id = $batchId` and insert one `StockMovement` row per batch deduction with `type = 'dispensed'`, a negative quantity, the invoice id, and the `unitPrice` snapshot — matching the movement shape Phase 5's dispense service writes so the stock history reconciles across both paths.

Return the deduction plan (`{ inventoryItemId, batchId, quantity, unitPrice }[]`) so the repository can stamp `invoiceId` and the void path can reverse it precisely.

`restoreToStock(tx, clinicId, invoiceId)` — the D-26 reverse: read the `dispensed` movements stamped with this invoice, add their absolute quantities back to the originating batches, and insert `type = 'returned'` movements with positive quantities.
