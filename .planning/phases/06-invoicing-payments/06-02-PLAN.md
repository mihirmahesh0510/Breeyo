<objective>
Wave 0c (D-30, the part 06-PATTERNS.md Warning 4 identified as the real root cause): make the tenant client actually be used.

`request.db` is set by `tenantContext` on every authenticated request and is consumed by exactly zero modules. `emr.routes.ts:12`, `queue.routes.ts:9`, `patient.routes.ts:9`, `drug.routes.ts:9`, `vaccination.routes.ts:9`, `attachment.routes.ts:8`, `notification.routes.ts:10` and `clinic.routes.ts:10` all construct their repositories with `fastify.prisma` — the `breeyo_admin` client, which bypasses row-level security by design — and `emr.controller.ts:263` reaches for `request.server.prisma` directly. Plan 06-00 fixed the tenant client; without this plan that fix changes nothing at runtime, and Phase 6's invoice, payment and Razorpay-credential tables would be added on top of a boundary that is demonstrably bypassed.

Purpose: an IDOR on billing data exposes another clinic's revenue. RLS is the second layer of the defence-in-depth the security research calls for; this plan makes the first layer real for the routes that already exist, and establishes the pattern that plan 06-08's billing routes will follow.
Output: per-request service construction from `request.db` across all eight clinic-scoped modules, an explicit exemption list for the three legitimate admin-client consumers, HTTP-layer cross-tenant tests, and a CI gate that prevents regression.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| authenticated HTTP request → repository query | The clinic identity carried in the JWT must constrain every row the query can reach |
| background job / cron → database | No request context exists; tenancy must come from the job payload and is not RLS-enforced |

| T-06-04 | Information Disclosure | `emr.controller.ts:263` `request.server.prisma.speciesDosage` | mitigate | Replaced with `request.db.speciesDosage`; grep gate asserts zero `request.server.prisma` occurrences |
| T-06-25 | Elevation of Privilege | dropping explicit `clinicId` filters after adding RLS | mitigate | Action forbids removing any existing `clinicId` filter; defence in depth is required by 06-RESEARCH.md's threat register (RLS plus explicit WHERE) |
| T-06-26 | Information Disclosure | BullMQ notification worker with no request context | accept | Workers derive `clinicId` from the durable job payload written by an already-tenant-scoped request; documented as a `D-30 exemption` comment and whitelisted in the gate rather than silently permitted |
