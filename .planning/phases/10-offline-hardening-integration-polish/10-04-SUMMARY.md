# Phase 10 Plan 04: Offline Stock Actions and FIFO-Safe Inventory Replay Summary

Made receive/dispense/adjust/return-to-stock stock actions survive real connectivity loss on top of Phase 5's existing offline barcode-lookup cache (`OfflineBarcodeCache`/`OfflineQueueService`, D-19, untouched): a new same-day working-set cache (`inventory_working_set_snapshot`, Plan 10-01's shared table) tracks stock-in-motion items and their not-yet-replayed local deltas, offline stock actions enqueue `INVENTORY_MEDIUM` replay envelopes into the SAME shared `sync_operations` ledger queue/EMR already use, and server-side reconciliation re-checks live FIFO/batch/expiry state through the SAME `FifoDispenseService`/`StockAdjustmentService`/`StockReceiptService` the online routes use (D-04) before applying anything, routing genuine mismatches into a lighter-weight `OPERATIONAL` review task (D-10) instead of silently overwriting stock truth.

Built strictly test-first: every acceptance criterion (including a FIFO-mismatch case and an idempotent-duplicate-replay case) had a failing test confirmed RED before its implementation was written.

## What Was Built

### Task 1: Offline stock action persistence + barcode-scanner wiring (TDD)

- **`apps/mobile/src/features/inventory/services/offlineStockActionStore.ts`** (new, RN-free — same pattern as `offlineConsultationDraftStore.ts`: only `expo-sqlite` types + `offlineDb.ts`, no `react-native`/`expo-secure-store`/`expo-haptics` import, so it is directly testable under vitest's plain-node environment): `recordOfflineStockReceive`/`recordOfflineStockDispense`/`recordOfflineStockAdjust`/`recordOfflineStockReturn` each apply a local optimistic delta to a `CachedStockWorkingSetItem` cached in the SAME `inventory_working_set_snapshot` same-day working-set table Plan 10-01 defined and Plan 10-03 added a read path for, then enqueue an `INVENTORY_MEDIUM`-tagged envelope (`STOCK_RECEIVE`/`STOCK_DISPENSE`/`STOCK_ADJUST`/`STOCK_RETURN`, domain `inventory`) into the shared `sync_operations` replay ledger. `cacheScannedStockItem` seeds the working set the first time an item is scanned this session (never clobbering an already-cached item's in-flight local delta with a possibly-stale server figure from a re-scan). Every action requires a `knownItem` snapshot to seed the cache the FIRST time it touches an item with no cached row yet — it throws rather than guessing, matching this repo's established "never silently fabricate a baseline" posture.
- **`apps/mobile/src/features/inventory/hooks/useOfflineStockActions.ts`** — `receiveStock`/`dispenseStock`/`adjustStock`/`returnToStock` each try the real online endpoint first (`POST /inventory/items/:itemId/receive|dispense|adjust`, `POST /inventory/movements/:movementId/return` — unchanged behavior on a healthy connection) and only fall back to `offlineStockActionStore`'s recorders on a genuine network failure (`isNetworkFailure`, the same `ApiClientError`-based classification `useOfflineQueueActions.ts`/`useAutoSave.ts` use). `getCachedItem`/`cacheScannedItem` expose the working-set cache read/seed path. A small `useInventoryOfflineSyncStore` (zustand) tracks a `pendingCount`, exposed as `visibilityState: SyncVisibilityState.PENDING | CAUGHT_UP` — the SAME shared `SyncVisibilityState` vocabulary Plan 10-02's `queueOfflineStore.ts` uses for its own marker, not a bespoke inventory-only enum (a dedicated per-domain store instance is consistent with queue's own precedent; it is the state enum that must stay shared).
- **`BarcodeScannerScreen.tsx`** wired to `useOfflineStockActions`: every resolved scan (online or from Phase 5's own offline barcode cache) seeds the Phase 10 working-set cache via `cacheScannedItem`, and a quiet `pendingCount > 0` badge ("N stock update(s) pending sync", `cloud-sync-outline` icon) renders below the existing offline banner — the same calm, non-blocking marker treatment `QueueCardItem.tsx` established for queue (D-19 to D-21). Scanning itself was ALREADY fully usable offline before this plan (Phase 5, D-19, `OfflineBarcodeCache`) — that path is left untouched; this plan hardens the STOCK-ACTION side D-04 also names.
- Tests: `offlineStockActions.test.ts` (15 — envelope tagging/domain/entityType per operation, working-set seed/read/accumulate across multiple actions, `cacheScannedStockItem`'s never-clobber-in-flight-delta rule, same-day scoping via `is_fully_editable`, `isNetworkFailure` classification, plus source-assertion coverage of `useOfflineStockActions.ts`'s `INVENTORY_MEDIUM`/recorder/`SyncVisibilityState` usage since that file's `react-native`/`expo-secure-store` imports make it untestable directly under vitest's plain-node environment, matching this repo's established convention for RN-locked files).

### Task 2: Inventory replay reconciliation and lighter operational review (TDD)

- **`apps/api/src/modules/inventory/services/inventoryOfflineReplay.service.ts`** (new) — `InventoryOfflineReplayService.replayInventoryOperation` validates the envelope with the shared `offlineOperationEnvelopeSchema`, checks idempotency against the SAME `SyncReplayReceipt` table Plan 10-01/10-02/10-03 all use (read/write directly, no second ledger), then dispatches on `entityType` (`STOCK_RECEIVE`/`STOCK_DISPENSE`/`STOCK_ADJUST`/`STOCK_RETURN`) to a small `InventoryOfflineReplayGateway` composed from the REAL `FifoDispenseService`/`StockAdjustmentService`/`StockReceiptService` — no FIFO/batch/expiry/stock-math logic is reimplemented here. `FifoDispenseService.dispense`'s existing row-locked (`FOR UPDATE`) live batch re-check is exactly where a stale offline decision meets current stock truth; this service's only added value is what happens when that re-check fails: a KNOWN mismatch error (`ITEM_NOT_FOUND`, `INSUFFICIENT_STOCK`, `VALIDATION_ERROR`, `MOVEMENT_NOT_FOUND` — matched by the structured `.code` every existing inventory service throws) is caught and routed into `InventoryConflictReviewService` instead of propagating as a raw failure; any OTHER (unexpected/infrastructure) error is rethrown unchanged, never silently swallowed into a false "reviewed" state. A receipt is recorded on BOTH the applied and the reviewed path, so a flapping replay of the same `operationId` is always an idempotent no-op.
- **`apps/api/src/modules/inventory/services/inventoryConflictReview.service.ts`** (new) — `InventoryConflictReviewService.summarizeMismatch` (+ `createInventoryReviewTask`) is deliberately far lighter than EMR's `clinicalConflict.service.ts` per D-10: no three-way field diff, no safe-merge computation, no mandatory named clinician owner. `INSUFFICIENT_STOCK` recommends `MANUAL_BATCH_CHOICE` (D-22: FIFO auto-select is the pragmatic default, but the system cannot silently guess a different batch/quantity on a live mismatch — a vet must); every other known mismatch recommends plain `MANUAL_REVIEW`. Persists into the SAME `SyncConflictRecord` table with `severity: OPERATIONAL` (never `SAFETY_CRITICAL`), mirroring `queueOfflineReplay.service.ts`'s own inline review-task shape but pulled into its own file per this plan's file list so it is independently testable.
- **`apps/api/src/modules/inventory/controllers/inventorySync.controller.ts`** (new) — `POST /inventory/sync/replay`, wired into `dispense.routes.ts` alongside the pre-existing Phase 5 `POST /inventory/sync-operation` dispatcher (both stay live side by side; neither replaces the other — see Deviation 1). `buildInventoryOfflineReplayGateway` composes the gateway adapter from the three real services (unlike queue's `QueueRepository`, no single existing inventory class already matches the four-method gateway shape 1:1). The handler defers any envelope whose `priority` isn't `INVENTORY_MEDIUM` untouched (mirrors `queueSync.controller.ts`'s own tier discipline) and returns `reviewTaskIds`/`rejectedOperations`/`deferredOperationIds` metadata on divergence.
- Tests: `inventoryOfflineReplay.service.test.ts` (15 — idempotent duplicate replay, the FIFO-mismatch case (`InsufficientStockError` → `REVIEW_CREATED` with an `OPERATIONAL`-severity review task, receipt still recorded), a live-overrideBatchId success case, receive/adjust/return APPLIED and REVIEW_CREATED cases, malformed/unsupported-entityType rejection, and an "unexpected error propagates, is never swallowed into a review" case, plus `InventoryConflictReviewService`'s mismatch-summary and review-task-creation behavior).

## Deviations From the Plan (flagged, not silently made)

1. **Phase 5's `POST /inventory/sync-operation` dispatcher (`sync-operation.service.ts`) was NOT replaced or touched.** The plan's context explicitly says Phase 5 "already has SOME offline caching" to harden/integrate with, not necessarily replace wholesale. Investigation confirmed Phase 5 already built a full, tested offline system for barcode scanning (`OfflineBarcodeCache`) and a Redis-idempotency-keyed pending-operations queue (`OfflineQueueService`, `SYNC_OPERATION_TYPES = ['receipt', 'dispense', 'adjustment']` — notably no `return` type) replaying through the generic `/inventory/sync-operation` dispatcher. Rather than migrating that live, working Phase 5 path onto Plan 10-01's newer shared ledger (a strictly riskier, broader change with no acceptance criterion requiring it), this plan added a SECOND, parallel replay surface (`/inventory/sync/replay`, `INVENTORY_MEDIUM`-tagged, `SyncReplayReceipt`-based) matching queue's (`/queue/sync/replay`) and EMR's (`/consultations/sync/replay`) Phase 10 pattern — the cross-domain contract this plan's acceptance criteria and `syncCoordinator.ts`'s priority ladder actually require. Both endpoints stay live; a future plan could migrate Phase 5's mobile queue onto the new hook if desired, but that migration is out of this plan's stated scope (Task 1's files are `offlineStockActionStore.ts`/`useOfflineStockActions.ts`/`BarcodeScannerScreen.tsx`, not `offline-queue.service.ts`).
2. **`DispenseScreen.tsx`, `StockReceiptScreen.tsx`, and `StockAdjustmentSheet.tsx` were NOT wired to `useOfflineStockActions.ts`.** The plan's `files_modified` list names only `BarcodeScannerScreen.tsx` for mobile screen changes; those three screens still call the online-only mutation hooks in `useInventoryApi.ts`/`useFifoDispense.ts` directly. `useOfflineStockActions.ts` is built, tested, and ready for those screens to adopt — this is the same class of scope note Plan 10-03 flagged for its resolution sheet's "merge safe fields" action (typed and ready, not yet wired everywhere it eventually belongs). `BarcodeScannerScreen.tsx`'s own quick actions ("Add Stock"/"Dispense") still navigate to those unwired screens via `router.push`, unchanged.
   **Verify-Fix Follow-Up (verify-fix 10.2, resolved):** all three screens now catch a genuine network failure (`isNetworkFailure`) from their existing online mutation and fall through to `useOfflineStockActions.dispenseStock`/`receiveStock`/`adjustStock` instead of only setting `serverError`, with a calm "queued -- will sync when back online" toast on the offline path (`getDispenseQueuedToast`/`getStockReceiptQueuedToast`/`getAdjustmentQueuedToast`, new pure-function toast copy in each screen's existing RN-free `lib/*.ts` module). `StockAdjustmentSheet.tsx` gained a required `category` prop (its route wrapper now passes `itemQuery.data.category`) since `StockActionKnownItem` needs it to seed the offline working-set cache. Return-to-stock was left untouched — no screen in this plan calls `returnToStock` (see Deviation 5 below; it requires an already server-known `movementId`, an accepted pre-existing limitation, not part of this gap). See `.planning/phases/10-offline-hardening-integration-polish/10-VALIDATION.md` row `10-04-01 (verify-fix 10.2)` and `.planning/PHASE-10-VERIFY-FIX-PLAN.md` finding 10.2.
3. **`cacheScannedStockItem` was added to `offlineStockActionStore.ts`, not named in the plan's acceptance criteria text.** Needed for `BarcodeScannerScreen.tsx`'s "reads from a local working-set cache when disconnected" criterion to mean something concrete beyond Phase 5's pre-existing (and already-offline-capable) barcode cache: without a Phase-10 write path seeding `inventory_working_set_snapshot` from a scan, nothing would ever populate that table for the scanner to fall back to. Built additively, alongside the plan's four named receive/dispense/adjust/return handlers, not instead of any of them.
4. **`InventoryOfflineReplayContext` carries an optional `userName`, absent from `QueueOfflineReplayContext`'s shape.** `FifoDispenseService`/`StockAdjustmentService`/`StockReceiptService` all take a `userName` parameter (a StockMovement display label, per Phase 5's `dispense.controller.ts` convention of `(request as any).userName ?? 'Unknown'`) that `QueueOfflineReplayContext` has no equivalent for. `buildInventoryOfflineReplayGateway` defaults it to `'Unknown'` when absent, matching the exact fallback the existing online dispense routes already use for the same field.
5. **Return-to-stock offline capture requires an already server-known `movementId`** (`StockReturnPayload.movementId`/`itemId`/`quantity`, all supplied by the caller from an existing `StockMovementTimeline` row, per D-57's UX). An item dispensed itself while still offline (its own dispense not yet replayed) cannot be returned offline in this plan — the same class of "reachable, not exhaustive" scope boundary Plan 10-02 documented for offline call-next (no live server to authoritatively pick "next") and Plan 10-03 documented for new-consultation creation (still requires connectivity).
