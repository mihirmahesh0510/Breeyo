**`scheduling.controller.ts`** — `export function createSchedulingController(appointmentService: AppointmentService, availabilityService: AvailabilityService)` returning a plain object of handlers, exactly like `createQueueController`. Copy the local `validationError(reply, issues)` helper. Every handler:
1. `safeParse` the body, params and query as applicable, early-returning `validationError` on failure.
2. Build the service params with `clinicId: request.user.activeClinicId` and `userId: request.user.id`. Never read `clinicId` from `request.body`, `request.params` or `request.query`.
3. Call the service and return `reply.status(...).send({ data })`. Use 201 for appointment and blocked-period creates, 200 for everything else.
4. Do not catch domain errors — `error-handler.ts` already turns the `Error & { statusCode, code }` shape into `{ error: { code, message } }`.

Handlers to expose:
- `listAppointmentsHandler` — `GET`, `appointmentRangeQuerySchema`. Returns `{ data: AppointmentWithDetails[] }`. This one endpoint serves the mobile day agenda (`from` and `to` one day apart) and the web week grid (seven days apart) per RESEARCH Pattern 4. Do not add separate day and week handlers.
- `getAppointmentHandler` — `GET` by `appointmentId`; a null service result becomes a 404 with `code: 'APPOINTMENT_NOT_FOUND'`.
- `getSlotsHandler` — `GET`, `slotQuerySchema`. Returns `{ data: SlotOption[] }` including the `isDoubleBooked` flags the booking UI renders as warnings.
- `createAppointmentHandler` — `POST`, 201, returning `{ data: { appointments, warnings } }` so the client can render the D-14 double-book strip and the D-22 truncation toast from the same response.
- `rescheduleAppointmentHandler` — `PATCH` by id.
- `cancelAppointmentHandler` — `POST` `/cancel` by id (a body-carrying cancel with a reason and a scope is not a `DELETE`).
- `updateAppointmentStatusHandler` — `PATCH` `/status` by id, dispatching to `checkInAppointment`, `completeAppointment` or `markNoShow` based on the target status. Reject any other status with `400 INVALID_TRANSITION` rather than silently ignoring it.
- `getAvailabilityTemplateHandler`, `putAvailabilityTemplateHandler` (by `vetId`) — returns `{ data: { template, affectedAppointmentCount } }` so the client can show the same "n appointments already booked" confirmation the override endpoint already provides (D-30).
- `putAvailabilityOverrideHandler` — returns `{ data: { override, affectedAppointmentCount } }` so the client can show UI-SPEC's "n appointments already booked" confirmation.
- `getBlockedPeriodsHandler`, `createBlockedPeriodHandler` (returns `{ data: { blockedPeriod, affectedAppointmentCount } }` (D-30) — the 201 status stays the same, only the response body's shape gains the count), `deleteBlockedPeriodHandler`.
- `getResolvedAvailabilityHandler` — `GET` returning the resolved hours plus blocked ranges for a date and optional vet, which is what the calendar surfaces need to grey out non-working cells.
- `listVetsHandler` — `GET`, returning the `id`-sorted vet list D-23's filter and the vet-colour assignment both depend on.

Do NOT expose any handler that calls `findDueForQueueHandoff`, `findExpiredExpected` or `findStartingSoon`. Those three repository queries are deliberately not clinic-scoped because a background worker calls them; reaching them from a route would be a cross-tenant read.
