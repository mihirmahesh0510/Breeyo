<objective>
Build the three cross-cutting primitives the rest of the billing module depends on: gap-free document numbering, at-rest encryption for per-clinic Razorpay credentials, and the dedicated financial audit log.

None of the three has an analog in this codebase. There is no `ON CONFLICT DO UPDATE`, no advisory lock and no `FOR UPDATE` anywhere in the repo today; there is no encryption at rest anywhere (argon2 is used for password hashing, which is a different primitive for a different purpose); and `audit-log.ts` targets the auth-centric `auth_audit_log` table.

Numbering cannot use a PostgreSQL `SEQUENCE`: sequences do not roll back, so a failed finalize burns a number and leaves a gap that a GST auditor will question under Rule 46(b)'s "consecutive serial number". A counter row with `ON CONFLICT DO UPDATE ... RETURNING` takes a row lock that serialises concurrent finalizes for the same clinic-month and rolls back with the transaction, which is gap-free at the cost of serialising finalizes per clinic — acceptable at solo-vet volume.

Purpose: D-15 and D-19 (numbering), D-29 and ASVS V6/V8 (credential encryption), D-32 (billing audit log). BIL-01, BIL-03, BIL-05 and BIL-06 all consume at least one of these.
Output: `numbering.service.ts`, `apps/api/src/lib/crypto.ts`, `apps/api/src/lib/billing-audit-log.ts`, and three test files including a real-database concurrency test.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| database column → Razorpay account | `razorpay_key_secret_enc` is a live payment credential; possession is authority to move money |
| environment → encryption key | `BILLING_ENCRYPTION_KEY` decrypts every clinic's credentials |
| concurrent transaction → counter row | Two simultaneous finalizes contend for the same document number |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-06-31 | Information Disclosure | Razorpay `key_secret` / `webhook_secret` at rest | mitigate | AES-256-GCM with a 32-byte key from `BILLING_ENCRYPTION_KEY`, fresh random 12-byte IV per encryption, `v1.` format marker for future rotation; grep gates assert no CBC, no legacy `createCipher`, no logging |
| T-06-32 | Tampering | ciphertext modification producing a substituted credential | mitigate | GCM auth tag verified on every decrypt; a single-character mutation test asserts `decryptSecret` throws rather than returning a value |
| T-06-33 | Information Disclosure | encryption key read at module scope, crashing or leaking on boot | mitigate | Key read lazily inside `getEncryptionKey()`; acceptance criteria assert the `process.env` read is inside a function body |
