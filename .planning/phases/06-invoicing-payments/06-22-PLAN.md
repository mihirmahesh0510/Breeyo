<objective>
Take the money, then show what happened.

Split from plan 06-17 for context budget: that plan owns the two detail hooks and the six status-gated presentation components; this plan owns the payment collection sheet, the refund and credit-note surfaces, and the detail and credit-note screens that compose everything. The seam sits where it does because the presentation components are independently renderable and the screens are pure composition plus flow wiring.

Two design decisions carry the weight. The digital payment flow renders the QR **on the device** from the Payment Link's `short_url` using `react-native-qrcode-svg` — no image is fetched, none is stored, no server CPU is spent, and it works from cached link data. Razorpay's QR Codes API is activation-gated and cannot be a Beta dependency across 20 pilot clinics.

The waiting-to-success transition is push, not poll: the webhook lands on the server, the server emits `invoice:updated` to the clinic's Socket.IO room, and the open sheet flips. The 15-minute countdown on screen is cosmetic — the server's per-minute sweep is what actually expires the link, because the front desk will background the app.

Purpose: BIL-05's collection surface, BIL-06's live confirmation, BIL-03's manual controls on the detail screen, and BIL-04's print and share entry points.
Output: two routes, two screens, eight components, and two test files.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| payment link response → device | Only the public `short_url` may reach the device; the key and secret must not |
| client-entered refund amount → money leaving the clinic | The client bound is a courtesy; the server bound is the control |
| socket event → "payment received" belief | What the front desk believes about payment determines whether they let the owner leave |
| credit-note line amounts → invoice balance | A credit above the original line total reduces revenue with no offsetting record |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-06-109 | Information Disclosure | a Razorpay key id or secret reaching client state or the rendered tree | mitigate | `QRCodeDisplay` accepts exactly three props and none is a credential; a test asserts the prop set; grep gate asserts no credential-shaped identifier appears in any billing component |
| T-06-110 | Tampering | the UI offering an action the invoice's state forbids, producing a 409 or an inconsistent belief | mitigate | `InvoiceActionBar` (plan 06-17) derives visibility from `isValidInvoiceTransition`; this plan's detail-screen test iterates all seven statuses against the table |
| T-06-111 | Tampering | a refund above the amount paid | mitigate | `makeRefundInputSchema(refundablePaise)` client-side plus the server's row-locked bound; a concurrent-refund 400 is surfaced as the documented failure copy rather than crashing |
| T-06-112 | Tampering | a credit amount above the original line total | mitigate | `CreditItemSelector` clamps to the line total with an inline error; the server enforces `CREDIT_EXCEEDS_LINE_TOTAL` |
| T-06-113 | Repudiation | showing a stale unpaid status after the webhook confirmed payment, causing a double collection | mitigate | The sheet's success transition is driven by the socket-invalidated invoice query; no polling interval exists, so there is no window where the client is knowingly stale |
| T-06-114 | Denial of Service | relying on the client countdown for expiry, leaving a pending payment forever when the app is backgrounded | mitigate | `PaymentLinkExpiryTimer` calls no API and is documented as display-only; the server's per-minute sweep owns expiry |
| T-06-115 | Tampering | voiding without the stock-restoration choice reaching the server | mitigate | The checkbox value from plan 06-17's `VoidConfirmSheet` is sent explicitly as `restoreStock`; a test asserts both `true` and `false` paths and their distinct toasts |
| T-06-116 | Information Disclosure | a generated PDF containing owner PII written to shared storage | mitigate | PDF writing is confined to plan 06-15's hook, which keeps files in the app's cache or documents directory |
</threat_model>
