# Phase 05 Plan 05: Barcode Scanner — Task 1 Summary (offline cache, queue, stores, sync hook)

**This summary covers Task 1 only** (offline barcode cache, pending operations queue, scanner/offline Zustand stores, `useOfflineSync` hook). Task 2 (camera screen + scanner components) is out of this task's scope and will append its own section to this file when built by a separate agent/session.

TDD applied per the orchestrator's explicit instruction: `offline-queue.service.test.ts` (FIFO replay order, stop-on-first-failure, `clientOperationId` generation) and `scanner.store.test.ts` (`isDuplicate`'s 1500ms window) were written first against a mocked `expo-sqlite` database and mocked `apiClient`, confirmed failing (`Failed to load url ... Does the file exist?`), then implementation was added until both were green.

## What Was Built

- **`services/offline-barcode-cache.ts`** — `OfflineBarcodeCache` class wrapping an expo-sqlite `barcode_cache`/`sync_meta` table pair. `syncFromServer(token)` calls `GET /api/v1/inventory/barcode-catalog?updatedSince=` (incremental — `updatedSince` is read from `sync_meta`'s last successful sync timestamp) and upserts one row per `(barcode, item)` pair from the response's `{ data: { items: [{ id, name, category, unit, currentStock, barcodes: [{code, format}] }] } }` shape (confirmed by reading `inventory-item.repository.ts`'s `getBarcodeCatalog()` directly — this is a reduced item shape, not the full `InventoryItem`). `lookupBarcode(code)`, `getLastSyncTime()`, `getCacheCount()` as specified. Exports `getInventoryOfflineDb()` — a lazily-opened, module-level-cached `expo-sqlite` database shared with the queue service (same `breeyo-inventory-cache` db, per the plan's "same database as barcode cache" instruction), so the app only ever opens one sqlite file for this feature.
- **`services/offline-queue.service.ts`** — `OfflineQueueService` class wrapping a `pending_operations` table. `enqueue(operationType, itemId, data)` generates and persists a per-operation `clientOperationId` (Math.random-based UUID v4 shape — no new native-crypto dependency needed for a non-security-sensitive idempotency key) and returns it. `getPendingCount()`, `getPendingOperations()` (bonus — not in the plan's literal export list but useful for a future retry-review UI per D-59), `syncPending(token)` replays unsynced rows in `created_at ASC` order through `POST /api/v1/inventory/sync-operation` with body `{ operationType, itemId, clientOperationId, data }` (the exact shape `SyncOperationService.execute()` expects, confirmed by reading `sync-operation.service.ts` and `dispense.routes.ts` directly), stopping at the first failure and returning `{ synced, failed, error? }` where `error` is a structured `PendingOperationError` (`clientOperationId`, `operationType`, `itemId`, `code`, `message`, `isConnectivityError`) — this is the D-59 "structured per-operation errors" support the task asked for. `clearSynced()` deletes rows already marked `synced=1`. Also exports `isConnectivityError(error)`, distinguishing a raw fetch-level `TypeError` (no network path to the server) from a structured `ApiClientError` (server responded, so the device IS online) — reused by `useOfflineSync`.
- **`stores/scanner.store.ts`** — `useScannerStore` (Zustand): `scannedItems` (newest-first via `addScannedItem`), `mode` (`'single' | 'continuous' | 'stockTake'`), `torchOn`, `lastScannedCode`/`lastScanTime`, and `isDuplicate(code)` checking a 1500ms window (`DUPLICATE_SCAN_WINDOW_MS`, exported constant) against the last scanned code — exactly per RESEARCH.md Pitfall 2 and the plan's spec.
- **`stores/offline-queue.store.ts`** — `useOfflineQueueStore` (Zustand): `pendingCount`, `lastSyncTime`, `isSyncing`, plus one addition beyond the plan's literal spec — `lastError: PendingOperationError | null` (and `setLastError`) — added because it's the most direct way for a future retry-banner component to surface the D-59 structured error the queue service already returns, without re-deriving it. No `persist` middleware (see Deviations).
- **`hooks/useOfflineSync.ts`** — `useOfflineSync()`: constructs (once, via refs) an `OfflineBarcodeCache` and `OfflineQueueService`, runs an initial sync on mount, re-syncs on every `AppState` transition to `'active'` (RESEARCH.md Pitfall 6), and polls every 30s while `isOffline` or `pendingCount > 0` (see Deviations — no netinfo-style library installed, so this hook derives connectivity from its own sync outcomes rather than a push event). Returns `{ isOffline, lastSynced, pendingCount, syncNow }` exactly as specified.

## What Was Built

- **`hooks/useBarcodeScan.ts`** — `useBarcodeScan({ mode, clinicId })` implementing the exact recommended flow from Task 1's summary: on `onBarcodeScanned(code)`, checks `useScannerStore.getState().isDuplicate(code)` first (skips the lookup entirely and reports a `duplicate` outcome, including the previously-scanned item's name when available, for the "toast, 1500ms" UI-SPEC copy); calls `setLastScanned(code)`; branches on `useOfflineSync().isOffline` — online via `GET /api/v1/inventory/barcode-lookup?code=`, offline via a locally-constructed `OfflineBarcodeCache().lookupBarcode(code)` — and additionally falls back from online to the offline cache if the live request itself fails with a connectivity-level error (`isConnectivityError`, reused directly from `offline-queue.service.ts`, not reimplemented). Normalizes whichever source resolved into a common `ScanResultItemView` (`{ code, itemId, itemName, category, unit, currentStock, parLevel, batchCount, nearestExpiry, source }`) via two pure functions, `toOnlineItemView`/`toOfflineItemView`, plus `computeNearestExpiry` (earliest expiry date across an item's active batches) — all three exported as `__testables` and covered by `tests/inventory/useBarcodeScan.test.ts`. On a found result: fires `Haptics.impactAsync(Medium)`, prepends to a local `scannedItems` list (full detail, for `ContinuousScanList`) *and* calls Task 1's `addScannedItem` (the store's minimal 4-field shape, so any other future consumer of `useScannerStore.scannedItems` still sees every scan). On not-found: fires `Haptics.notificationAsync(Warning)`. Returns `{ onBarcodeScanned, scannedItems, lastResult, isLooking, actualCounts, setActualCount, dismissResult, clearScanned }` — a superset of the plan's literal `{ onBarcodeScanned, scannedItems, lastResult, isLooking }` sketch (see Deviations).
- **`components/ScanRegionOverlay.tsx`** — full-screen semi-transparent (`rgba(0,0,0,0.6)`) overlay built from three stacked sections (dark top, a row of dark/clear-cutout/dark for the centered 70%-width × 25%-height scan region, dark bottom with "Point camera at barcode" text), using `react-native-reanimated`'s `useSharedValue`/`withSequence`/`withTiming` to pulse the cutout's border color from white to primary green and back over 300ms (`Easing.bezier(0.4, 0, 0.2, 1)`, per the UI-SPEC animation table) whenever an optional `pulseTrigger` prop changes.
- **`components/ScanResultBottomSheet.tsx`** — a real `@gorhom/bottom-sheet` wrapper (not `@breeyo/ui`'s `BottomSheet`, which is a non-gesture stub per its own doc comment — see Deviations): `snapPoints={['30%', '60%']}`, `index={-1}`, `enablePanDownToClose`, `enableDynamicSizing={false}` exactly per RESEARCH.md Pitfall 1, wrapping children in `BottomSheetView`. Exposes its ref type as `React.ElementRef<typeof BottomSheet>` (the library doesn't export a `BottomSheetMethods` type from its package root) so the screen can call `.snapToIndex(0)` to reveal it.
- **`components/ScanResultCard.tsx`** — item name, color-coded "In stock: N unit" (reusing `@breeyo/types`'s `getStockLevelStatus`, the same helper `InventoryItemCard.tsx` already uses, not a re-derived threshold table), "M batches · Exp: DD MMM YYYY" (or "Batch details unavailable offline" when `batchCount` is null), and the three quick-action buttons ("Add Stock" outlined, "Dispense" filled, "View Details" text).
- **`components/ManualBarcodeInput.tsx`** — numeric (`keyboardType="number-pad"`) `TextInput` + "Look Up" button, controlled by a `visible` prop (the screen owns the "Enter Barcode" toggle trigger and the boolean state — see Deviations on why the toggle itself isn't inside this component).
- **`components/UnknownBarcodePrompt.tsx`** — "Item not found" / "No item matches this barcode." / the scanned code / offline caption ("You may need to sync when online.") / "Try Again" (text) / "Create New Item" (filled) actions, per D-14 and the UI-SPEC copy table.
- **`components/ContinuousScanList.tsx`** — `FlatList` of `ScanResultItemView`s with a "Scanned Items (N)" header; each row shows item name + color-coded stock, and either the three quick-action buttons (continuous mode) or a "System: N unit" + "Actual Count" numeric input + color-coded discrepancy (stockTake mode, D-38).
- **`screens/BarcodeScannerScreen.tsx`** — full composition: mode from the route param (`useLocalSearchParams<{ mode?: string }>()`, validated against `['single','continuous','stockTake']`, default `'single'`), `useCameraPermission()`/`useCameraDevice('back')` from `react-native-vision-camera`, `useBarcodeScanner()` from `@mgcrea/vision-camera-barcode-scanner` filtered to `VISION_CAMERA_BARCODE_TYPES` (D-15, 1D formats only) with `scanMode: 'continuous'` (Task 1's Zustand-store-based 1500ms window handles de-duplication, not a scan-once mode), torch toggle wired to `useScannerStore`'s `torchOn`/`setTorch`, the offline banner + "Last synced: N min ago" staleness caption (>5 min, per the Barcode Scanner Performance Requirements table), the manual-entry toggle trigger + `ManualBarcodeInput`, and a `ScanResultBottomSheet` whose content switches between `ScanResultCard` (single mode, found), `UnknownBarcodePrompt` (not-found, any mode), or `ContinuousScanList` (continuous/stockTake). Both fallback states are implemented as full-screen views (no camera mounted at all): no-device shows `ManualBarcodeInput` forced-visible with a "Camera not available" message; permission-denied shows a request-permission button (while `canRequestPermission`) or an "Open Settings" link (`Linking.openSettings()`) once the OS has permanently denied it — adapting `PetPhotoPicker.tsx`'s request→check→guide-to-settings pattern to a full-screen gate instead of a modal action sheet, since the whole screen (not just a photo field) needs to be gated.

# Architecture Fix: react-native-vision-camera -> expo-camera (post-Task-2)

**Date:** 2026-08-13. **Trigger:** Task 2's own "Deviations" section (above) flagged a blocking dependency conflict but shipped anyway with a type-cast bridge; this fix resolves it for real rather than leaving it as a known-broken runtime path.

## The problem, precisely

The installed `react-native-vision-camera@5.2.2` is not an older/newer version of the classic API -- it is a **Nitro-architecture rewrite**. Directly reading `node_modules/react-native-vision-camera/lib/index.d.ts` confirms it exports only Nitro-spec hooks (`useFrameOutput`, `useObjectOutput`, etc.) and a `<Camera>` component with `device`/`isActive`/`outputs`/`torchMode` props -- **there is no `frameProcessor` prop at all**, and it requires the peer package `react-native-nitro-modules`, which was never installed in this repo. RESEARCH.md's own "Open Question 1" anticipated exactly this risk ("VisionCamera V5 + Expo SDK 52 stability... very recent... Fallback: expo-camera CameraView") and named the fallback that this fix implements.

## Is `CameraView.onBarcodeScanned` really continuous (not single-shot)? -- Yes, verified from source

Read `node_modules/expo-camera/build/CameraView.js` directly (not just the `.d.ts`/docs prose). The relevant logic:

```js
const EventThrottleMs = 500;
// ...
_onObjectDetected = (callback) => ({ nativeEvent }) => {
  const { type } = nativeEvent;
  if (this._lastEvents[type] &&
      this._lastEventsTimes[type] &&
      JSON.stringify(nativeEvent) === this._lastEvents[type] &&
      new Date().getTime() - this._lastEventsTimes[type].getTime() < EventThrottleMs) {
    return;                       // skip: same payload, within 500ms
  }
  if (callback) {
    callback(nativeEvent);        // fires -- new/different barcode, or >500ms elapsed
    this._lastEventsTimes[type] = new Date();
    this._lastEvents[type] = JSON.stringify(nativeEvent);
  }
};
```

This throttles *repeated identical* barcode payloads to at most once per 500ms -- it is **not** a scan-once/disable-after-first-hit gate. A different barcode (or the same barcode again after the 500ms window) fires the callback again immediately, for as long as `<CameraView>` stays mounted with `onBarcodeScanned` set. That is genuine continuous scanning at the native-bridge level. It composes correctly underneath Task 1's `useScannerStore.isDuplicate()` 1500ms app-level dedupe window (500ms native throttle < 1500ms app dedupe, so the app-level window is always the binding constraint, exactly as intended) -- this is what D-18's continuous scanning mode and D-38's stock-take scanning mode both rely on.
