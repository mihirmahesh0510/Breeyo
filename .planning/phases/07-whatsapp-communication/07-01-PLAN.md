## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| migration tooling → production database | A generated migration can drop or rewrite tables holding clinic data |
| breeyo_app role → whatsapp_* tables | Application queries reach new tables through the least-privileged role |
| clinic A rows → clinic B queries | Tenant isolation depends on clinic_id columns and indexes existing on every new table |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-07-01-01 | Denial of Service | backfill migration SQL | mitigate | Generate with `--create-only`, inspect for `DROP TABLE`/destructive `ALTER` before applying; acceptance criteria asserts zero `DROP TABLE`; blocking human checkpoint before the phase proceeds |
| T-07-01-02 | Information Disclosure | whatsapp_threads / whatsapp_messages cross-tenant read | mitigate | Every model carries `clinicId` with clinicId-leading composite indexes; enforcement is the explicit-clinicId repository pattern added in later plans (Pitfall 5 — FORCE RLS would break `fastify.prisma` access and is deliberately not used) |
| T-07-01-03 | Tampering | duplicate inbound webhook creating duplicate messages | mitigate | `provider_message_id` UNIQUE on whatsapp_messages so a redelivered Meta webhook fails with P2002 and is treated as already-processed |
| T-07-01-04 | Elevation of Privilege | second booking request stealing a held slot | mitigate | `@@unique([clinicId, slotDate, slotStartMinutes])` on whatsapp_slot_holds makes Postgres, not application code, the arbiter of D-07 |
| T-07-01-05 | Denial of Service | unbounded automated reminder sending (nag loop / Meta quality damage) | mitigate | `@@unique([clinicId, sourceType, sourceId, kind, touch])` plus `escalationMaxAttempts` default 2 and `CAPPED_NEEDS_ACTION` state make repeated sends structurally impossible (D-03/D-04) |
| T-07-01-06 | Repudiation | message status history rewritten | mitigate | `whatsapp_message_status_events` is append-only with `occurredAt`; no update path is modelled |
| T-07-01-SC | Tampering | npm/pip/cargo installs | mitigate | Zero new packages in this phase (07-RESEARCH § Package Legitimacy Audit: all candidates evaluated and rejected). If any install becomes necessary, slopcheck with `-e npm` plus a blocking human checkpoint is required before install |
